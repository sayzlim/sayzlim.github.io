My chezmoi setup, seven months later

In April I wrote that chezmoi makes dotfiles act like infrastructure. Here is what that looked like after seven months of real use across two Macs.

Sayz Lim Nov 17, 2026
  • Development

In April I wrote about how I use chezmoi to manage dotfiles across Macs. It ended with a claim: once the maintenance loop clicks, dotfiles stop feeling like a side project and start acting like infrastructure.

Seven months later, I can check that claim against the repo instead of my memory. Most of its history was written after that post.

What held up

The basics did not change.

The source repo is still the truth. The naming scheme still reads fine once you stop noticing it. The loop is the same: manage, apply, inspect drift, sync back. Karabiner, my global Git ignore and ~/.config/git/ignore are still managed exactly as I described.

That part was right. What changed is everything around it.

The setup tells me when it drifts

In April, drift was something I had to remember to check with chezmoi diff. That is the weak point of any setup that depends on remembering.

Now a new terminal tells me. When this Mac has fallen behind the repo, has unpushed or uncommitted changes, or differs from what chezmoi would apply, I get one line:

dotfiles: 2 behind (chezmoi update), 1 changed (chezmoi diff)

Each part names the command to look at next. When everything matches, it prints nothing.

The fetch behind it runs in the background, at most every 15 minutes, so opening a terminal never waits on the network. And if fetching or checking fails, it says so, because a failing check that printed nothing would look exactly like a clean machine.

This is the change I would make first if I started again. Drift you have to go looking for is drift you find late.

Changes go through pull requests

Since late September, every change to the dotfiles lands as a pull request, the same way changes land in my other repos.

That sounds heavy for config files. It isn’t, and the reason is what the dotfiles now carry. A change to my Git config decides how every repo on both Macs authenticates. A change to my shell runs on every terminal I open. Those deserve the same review as code, because they behave like code.

It also gives me a history I can read. Each change has a title that says what it does and a description that says why.

Templates arrived when a real difference did

In April I listed “over-templating too early” as a mistake. That advice held, and now I can say why: each template I have today arrived with a concrete reason, not in anticipation of one.

  • My Git config looks up where gh is installed, because apps launched outside a terminal do not see my shell’s PATH. If gh is missing, the apply stops and tells me what to install, instead of writing a broken config.
  • The Codex config is managed with a modify template that sets only the model settings. Codex writes its own per-machine entries into the same file, so owning the whole file would mean fighting it on every apply.
  • One Mac has less memory available to Docker than the other. That difference lives as a flag in each machine’s local chezmoi config, not in the shared repo.

Not everything needed a template. My work email applies automatically in work repositories through Git’s own includeIf, matched on the repository’s remote. Git already solved that one.

The setup now includes my AI tools

The biggest category of change was not shell or Git config. It was the rules I give Claude Code and Codex: how they report progress, when they stop and ask, what they must never do without me.

Those rules are configuration in the most literal sense. They change how my tools behave on every project. And they drift like any other config: a rule added on one Mac and not the other means the same request behaves differently depending on where I am sitting.

So they live in the dotfiles now, reviewed like everything else.

Smaller things

  • A Brewfile lists the Homebrew formulae the dotfiles depend on, and nothing else. brew bundle check --no-upgrade tells me whether a Mac is missing one.
  • mise pins Node, pnpm and Python, so both Macs run the same versions.
  • Aliases moved into their own file, and WezTerm joined the managed set.
  • Git now fetches and pushes GitHub over HTTPS with the GitHub CLI’s login. 1Password still signs my commits, but it no longer needs to unlock an SSH key every time I pull.

One correction

In April I wrote that my commit helper scripts were part of what I wanted chezmoi to keep in sync. They ended up somewhere else: a repository of their own, installed onto each Mac. They grew tests and their own review process, and they are tools rather than configuration.

The line is not perfectly clean. chezmoi still carries a few scripts that exist only to run my work setup on these two Macs. But the helpers I use across every project now live where they can be developed and tested on their own.

The takeaway

The April post was about a loop: manage, apply, inspect drift, sync back. That loop still works. What seven months added is that I no longer have to be the one who remembers to run it.

The setup tells me when it has drifted. Every change since late September is reviewed. Templates exist only where there is a concrete reason.

That is what I meant by infrastructure. Not a clever setup, but one that keeps telling the truth about itself.
